# Math Study Log 数式 OCR 比較

**追加候補の調査。** PP-FormulaNet_plus-L は公式公開モデルで、公開評価では M より高い BLEU と長い推論時間が示される。今回は必須の S・M を優先した。RapidLaTeXOCR は LaTeX-OCR の ONNX 実装でコードは MIT。変換済み重みについて独立した再配布許諾を確認できなかった。TypLens V1.1 は MFR 1.5 由来の MIT 表記の Typst 出力モデルで、33.1 MB のコンパクト ONNX が公開されている。LaTeX 変換を減らせるため次回の比較候補になる。これら3つは今回の実測順位に含めていない。[Paddle 公式比較](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/formula_recognition.html) · [公式 L](https://huggingface.co/PaddlePaddle/PP-FormulaNet_plus-L) · [RapidLaTeXOCR](https://github.com/RapidAI/RapidLatexOCR) · [TypLens モデルカード](https://huggingface.co/dbcccc/TypLens)

**公開値の読み方。** Paddle 公式表の英語 BLEU は S 88.71、M 91.45、L 92.22。公開 CPU 高性能モードの時間はそれぞれ 261、1,616、3,126 ms。現行 IBEM の配布元は FP32 の独自検証セットで完全一致 92.63% と報告している。いずれも今回の構文木一致率とはデータ、実行構成、指標が異なる。[Paddle 公式比較](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/formula_recognition.html) · [IBEM モデルカード](https://huggingface.co/dbcccc/IBEM-im2typst)

## 評価方法

- Windows 11 x64 build 26200、Core i7-13620H、論理16コア、RAM 約32 GiB、GeForce RTX 4060 Laptop GPU 8 GiB。CPU 比較は各ランタイムの推論スレッド設定を1にし、モデルごとに別プロセスで順次実行した。IBEM の CPU は INT8、WebGPU は FP16。その他は取得した公式重みを使用した。
- 実行環境は Electron 45.2.3 または Python 3.12.12。Paddle は PaddlePaddle 3.3.1、PaddleOCR 3.7.0、PaddleX 3.7.2 の静的推論で、oneDNN を無効にした。Pix2Text は CPU が ONNX Runtime 1.31.1、DirectML が1.24.4。pix2tex は0.1.4、PyTorch CPU 2.8.0。全依存の固定版は [再現手順](../bench/ocr/README.md) から参照できる。
- 34問、40 PNG。縦組み分数、指数、根号、暗黙の乗算、積分・極限、三角関数、対数、等号・減算、括弧、問題番号、日本語指示、表示倍率相当のサイズ変更を含む。数式単体では各モデルに同一の PNG を渡し、正解と画像のハッシュを照合した。番号・日本語の分離は別評価。
- 完全一致は、先頭末尾の空白だけを除いた形式別正解との一致。空白をすべて除いた一致も参考として計算する。構文木一致では暗黙の乗算と明示の乗算、表示用の LaTeX 指定、余分な括弧を許容する。式変形、可換項の並び替え、指数や符号の補完は行わない。
- 重大演算子誤りは、解析できた候補で加減算・単項負号・等号・不等号の種類と出現数が正解と異なる件数。構造破綻は分数・指数・根号・積分・極限の部分木が異なる件数。同じ個数の演算子を誤った位置に置いたケースは構文木一致の失敗に含む。解析不能は独立して計数するため、重大演算子誤りと構造破綻の件数は下限。
- 初期化はモデルをロードする区間。Python 版ではライブラリの初回 import を含み、IBEM では起動済みの Electron 内での Worker 初期化から測る。初回推論と、残り33問の中央値・p90を分けた。Python は画像読み込みから出力まで、IBEM は Renderer に渡した PNG の Worker 処理を計測し、ディスク読み込みと画像の受け渡しは含まない。
- メモリは Python が Windows のプロセスのピークワーキングセット。IBEM は Electron の全プロセスのワーキングセットの合計を100 msごとにサンプリングした値で、共有メモリが重複して数えられ得る。GPU の専用メモリは別途未計測。初期化・メモリとも同じ計測範囲の値として扱わない。

### 指定3問

番号付きの問題は、番号を含む共通画像から固定位置で切り出した数式を入力した。この表は数式認識の結果であり、番号検出の成功を意味しない。次の出力は CPU の実測。

| モデル | ① 縦組み分数 | ② 暗黙の乗算 | ③ 縦組み分数と文字の積 |
| --- | --- | --- | --- |
| IBEM | `frac x ^2 , x - 5*x + 6 , 2` | `3 ⟦a(2*a - b)⟧ - 2 ⟦b(a + 3*b)⟧` | `((2 a ⟦b(a + b)⟧)/(a))` |
| S | `\frac{x^{2}-5x+6}{x-2}` | `3a(2a-b)-2b(a+3b)` | `\frac{2a b(a+b)}{4a}` |
| M | `\frac{x^{2}-5x+6}{x-2}` | `3a(2a-b)-2b(a+3b)` | `\frac{2a b(a+b)}{4a}` |
| Pix2Text | `\frac { x ^ { 2 } - 5 x + 6 } { x - 2 }` | `3 a ( 2 a - b ) - 2 b ( a + 3 b )` | `\frac { 2 a b ( a + b ) } { 4 a }` |
| pix2tex | `\frac{x^{2}-5x+6}{x-2}` | `3a(2a-b)-2b(a+3b)` | `\frac{2a b(a+b)}{4a}` |

構文木一致は IBEM 0/3、他の4モデルは3/3。②の IBEM は元の Typst に文字・減算・括弧を出していたが、既存の正規化が `a(…)` と `b(…)` を未対応構造として残した。③では元の Typst の時点で分母の係数4が欠落した。

### 問題番号・日本語を含む画像

番号や日本語を含む同一の6枚を、切り出さずに各数式モデルにも直接入力した。単一数式として構文木が一致する出力は全モデル0/6だった。Paddle M は番号だけが付いた3枚で、番号と分数を別行の LaTeX として保持した。Paddle S は①で同様の出力を返した。Pix2Text は①と③で番号を分子側に取り込んだ。日本語指示がある画像では LaTeX の多行構造、混在した文字、または長い反復が出たため、直接入力から日本語指示を安全に取り出せる根拠は得られなかった。

別途、現行 Windows 版の混在 OCR では、日本語指示を含む3枚すべてで指示文が一致した。数式も含めた全体の一致は0/6。①と2倍サイズの③は領域分割で止まり、通常サイズの③では分子の一部が指示文側に入った。次の統合試験では、候補モデルに渡す数式の切り出しと、Tesseract の結果を分けて検証する。

### 選定

- **A 精度優先は Pix2Text MFR 1.5 と Paddle M の同率。** どちらも31/34で、指定3問は全問正解。Paddle M は字面一致で上回るが、Pix2Text は今回の積分と暗黙の乗算で上回った。34問の合成画像から総合的な精度差は確定できない。
- **B 速度優先は配布条件を満たす実測候補の中で Paddle S。** CPU 中央値612 ms、構文木29/34。pix2tex は406 msで最速だが公式重みの用途に非商用条件がある。IBEM WebGPU は465 msだったが構文木7/34で、精度を保つ速度候補にはしない。
- **C 総合推奨は Pix2Text MFR 1.5 を CPU 既定で試験統合。** M と同じ構文木31/34、M より約3.3倍短い CPU 中央値、約5分の1のモデルファイル。S より中央値は約0.20秒長いが、構文木一致は2件多く、重みが小さく公式 ONNX が使える。DirectML の中央値改善は約59 msで、p90と初回推論は CPU より長かった。この測定では GPU を既定にする利点を確認できなかった。

M と Pix2Text は共通で29問正解し、一方だけ正しい問題が各2問あった。正しい側を毎回選べた場合の上限は33/34。今回の計測からは自動で安全に選ぶ根拠が得られていないため、次の試験は Pix2Text 単体から始める。

## 次の Codex タスクで行う統合試験

1. 試験用の明示設定で Windows OCR ホストに Pix2Text を接続する。設定を切り替えるまでは現行経路で起動できるようにする。公式 ONNX のリビジョンとハッシュを確認し、配布準備では MIT 表示と依存の通知を同梱する。
2. `desktop/ocr-host/host.js` と新規の Pix2Text Worker アダプターで、RGB の384×384 bicubic、正規化、ONNX エンコーダー・デコーダー、固定トークナイザー、BOS/EOS、生成上限を再現する。まず同梱 ONNX Runtime Web の WASM で今回の CPU 出力との全34問の一致を確認する。非対応演算があれば分離した Node 側 ONNX ワーカーを比較する。
3. `desktop/services/local-ocr.js` のローカル資産許可リストを追加モデルの必要ファイルだけに広げる。CPU 実行、キャンセル、タイムアウト、Worker 破棄、モデルロード失敗、ネットワークなし起動を検証する。Electron のサンドボックスと IPC の入力検証を使う。
4. 新規の LaTeX 正規化器に、分数、根号、指数、演算子、明示の構造を保つ変換を追加する。`\cfrac`、`\underset`、`\operatorname` の既知の用法をテストし、未対応コマンド・不完全な入力・立方根の指数欠落を勝手に補完しない。元の LaTeX と候補をプレビューで照合できるようにする。
5. `js/ocr/mixed-image-segmenter.js` と Tesseract の構成で、番号付き分数の上下が別問題として誤分割されるケースを実画面で検証する。候補モデルの数式精度と切り出し精度を独立に追跡する。
6. `tests/desktop-ocr-workflow.test.mjs` と `scripts/windows-ocr-smoke.mjs` に、実画像でのトレイ・スクリーンショット・候補確認・コピー・計算の確認を追加する。実際の教材、PDF ビューアー、Word の数式を含む未使用画像を追加し、今回の誤りが残る符号・根号を重点的に検証する。試験導入中は候補を画像と確認してからコピーし、計算は既存の別操作で行う。

本比較で測ったのは合成された印刷数式と単一端末。学習済みモデルの本番置換の判断には、異なるハードウェア、未使用の教材画像、実際の切り出し、ウォームワーカーと低メモリ時の計測が残る。
